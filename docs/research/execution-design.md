# Execution/API repair design — evidence checked 2026-09-06

Read-only investigation of `/home/vilius/projects/5min-btc-polymarket`; no bot, order, wallet setup, approval, redemption, or dependency installation was executed. Public GETs and one read-only Polygon RPC `eth_chainId` request were made. This is an implementation recommendation, not evidence of a profitable strategy.

## Recommendation

Make this repository own one Python process using **`polymarket-client==0.9.0`**, Python 3.11+, and a local SQLite ledger. Keep the strategy, market data, execution, recovery, and reporting in process. Remove the missing external trading runner from the critical path. Use the unified SDK's async clients for public streams plus authenticated order/account calls, and its separate `create_*` and `post_order` methods so order intent is durable before network submission.

The official package is `polymarket-client`, imported as `polymarket`. PyPI returned 0.9.0, uploaded September 4, 2026; GitHub release tag `polymarket-client-v0.9.0` points to `8b4fa35045dfba48014dc3067004fb641ca123cf`. It supports Gamma, Data API, CLOB and RTDS together. Pin the release; 0.x minor releases can break interfaces. Its dependencies already include `httpx`, `websockets`, `eth-account`, `eth-abi`, `eth-utils`, and Pydantic, so no second SDK, separate WebSocket library, web3 package, dataframe stack, or exchange-price dependency is necessary. [Official SDK](https://github.com/Polymarket/py-sdk), [release package](https://pypi.org/project/polymarket-client/0.9.0/), [pinned project metadata](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/pyproject.toml).

The older `py-clob-client-v2` remains the dedicated V2 CLOB client but now recommends the unified SDK for new work. The repository's `py_clob_client` imports predate the April 28 CLOB V2 cutover. Production continues at `https://clob.polymarket.com`; the old V1 signing format is unsupported. pUSD is the current trading collateral. Do not confuse the current market-info response's `v:"v1"` (CTF market protocol) with a requirement to use the obsolete CLOB V1 SDK. [V2 client README](https://github.com/Polymarket/py-clob-client-v2), [CLOB migration](https://docs.polymarket.com/v2-migration), [SDK asset/protocol selection example](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/examples/create_market_order.py).

## What the BTC market actually resolves on

September 6 market rules explicitly identify **Chainlink BTC/USD TWAP 60s**: `https://data.chain.link/streams/btc-usd-twap-60s-streams`. Up wins on a greater-than-or-equal comparison against the beginning price; otherwise Down. Do not use Binance BTCUSDT, a Chainlink spot topic, a local average of spot ticks, or a five-minute arithmetic average as if it were the settlement series. [Current market rules](https://polymarket.com/event/btc-updown-5m-1788705900).

The market lasts five minutes; the identified feed's averaging lookback is **60 seconds**, not five minutes and not its publication interval. Chainlink's exact custom-feed sampling boundaries, weighting, rounding, and missing-input behavior are not public. Therefore use Chainlink-computed values. The rules and stream docs do not fully specify which boundary observation is selected when the exact opening/closing timestamp is missing. Do not silently claim “first tick received after start” is the official opening anchor.

### Free reference-price integration

Use `AsyncPublicClient.subscribe(CryptoPricesChainlinkTwapSpec(window_seconds=60, symbols=["btc/usd"]))`. Direct RTDS is `wss://ws-live-data.polymarket.com`; wire topic `crypto_prices_twap_sixty`, `type:"update"`, compact filter string `{"symbol":"btc/usd"}`. Application heartbeat is text `PING` every five seconds. SDK reconnects/resubscribes, but the service sends only subsequent updates: **no snapshot, history or replay**. Preserve `payload.value` as Decimal, use `payload.timestamp` for observation age and local monotonic receipt time for network health. Raw wire precision is `full_accuracy_value / 10^18`. No paid Chainlink credentials are required through Polymarket RTDS. [Official TWAP integration](https://docs.polymarket.com/market-data/chainlink-twap), [pinned subscription mapping](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/_internal/streams/rtds/protocol.py).

Recommended anchor policy (design, not a published exchange guarantee): start recording before the next slot; retain exact boundary observations and their source times; compare recorded candidates against later official `priceToBeat` over a read-only sample. Prefer Gamma's matching-slot priceToBeat once present, but never borrow another slot's anchor. If only a recorded approximation exists, mark it explicitly and require demonstrated boundary agreement before enabling the move-based live strategy. If no trustworthy anchor exists, skip the slot. Do not interpolate across a stream outage and label it official. Keep historical anchor/final metadata for audit.

The undocumented website `/api/crypto/crypto-price?...&variant=fiveminute` returned HTTP 429 in a single read-only probe. It has no established public SDK contract here; do not make the bot depend on it. Direct Chainlink report/history access requires standard or sponsored credentials; “free RTDS” does not imply free credentialless Chainlink history.

Optional faster spot momentum can use the same SDK's `CryptoPricesSpec(topic="prices.crypto.binance", symbols=["btcusdt"])` or Chainlink spot topic. Treat those as different features with their own timestamps, never a replacement anchor. The minimum implementation needs only TWAP60s plus the two outcome books. [SDK stream specifications](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/streams/_specs.py).

## Safe order submission and recovery

Use marketable, price-protected orders: `create_market_order(asset_id=..., side="BUY", amount=..., max_spend=..., max_price=..., order_type="FOK")`, or `side="SELL", shares=..., min_price=..., order_type="FAK"`. FOK (fill or kill) reduces entry partials; FAK (fill and kill) exits available quantity immediately and discards the rest. Both still need acknowledgement and settlement handling. Do not fall back automatically to an indefinitely resting GTC order or a one-cent panic price. SDK limit-order expiration requires at least three minutes in the future, which is inconvenient for a late-entry five-minute bot. [Place orders](https://docs.polymarket.com/trading/place-orders), [pinned order validation/building](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/_internal/actions/orders/market.py).

**Important SDK behavior:** `place_limit_order` / `place_market_order` convenience paths can recover an allowance error by sending an unlimited collateral approval or ERC1155 approval-for-all, then reposting. `post_order(signed_order)` does not perform that recovery. Use explicit allowance preflight/setup and the latter submission path; setup must never happen as an unexpected trading-loop side effect. [Actual recovery implementation](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/_internal/actions/orders/place.py).

Proposed sequence:

1. Acquire a process lock and recover all prior nonterminal orders/inventory before evaluating another signal.
2. In a SQLite transaction, reserve the maximum intended exposure and create a unique intent associated with run, round, condition, side and configured caps. No parallel opening intent for that round.
3. Create/sign locally, then persist the **exact signed payload**, exchange domain and canonical order hash, commit it, then mark submitting before the HTTP call. Keep signed payload access restricted; never put secrets or replayable orders in ordinary logs.
4. Submit once. An accepted order is tracked, not immediately classified as settled. An explicit rejection can release the reserve after ruling out fills. A timeout, connection reset, unparseable success body, or ambiguous 5xx becomes `SUBMIT_UNKNOWN` and freezes new entries.
5. Reconcile by deterministic order hash using get-order, own open orders, account trades and, if necessary, receipt events. Do not sign a new replacement until the previous exposure is resolved. “Not found once” is not evidence of no order. A restart follows exactly the same path.
6. Record each fill once. Keep matched-but-unsettled exposure reserved. Trade `CONFIRMED` is success; `FAILED` is terminal failure; `MATCHED`, `MINED`, and `RETRYING` are not final. A failed receipt/fill must reverse provisional inventory/accounting.
7. For every close attempt, subtract all already confirmed sells and reserve outstanding sell quantity. Cancel only the bot's recorded order IDs, confirm cancellation, then re-fetch fills and inventory before replacing; cancellation cannot undo matched quantity.
8. Mark flat only when no opening/closing orders remain and reconciled actual token inventory is zero (or explicitly recorded unavoidable dust). Unclosed inventory is a visible unresolved state, never `done`.

The CLOB order ID is the order hash. Official CTF V2 contract `hashOrder(Order)` computes it from the EIP-712 domain and order struct; signature and API expiration are not part of that hash. The unified Python SDK currently has no public `get_order_hash` method. Implement one tightly scoped adapter using existing eth-account/eth-abi dependencies and the official struct, or verify against read-only `eth_call` to exchange `hashOrder`. Test synthetic known vectors and verify the first actual acknowledged order ID. This deterministic hash is necessary for robust recovery after a lost POST response. Avoid depending on an undocumented duplicate-order replay response. [Order endpoint contract](https://docs.polymarket.com/api-spec/clob-openapi.yaml), [official hash function](https://github.com/Polymarket/ctf-exchange-v2/blob/main/src/exchange/mixins/Hashing.sol), [signed struct](https://github.com/Polymarket/ctf-exchange-v2/blob/main/src/exchange/libraries/Structs.sol).

`wait_for_order_fill_settlement()` is useful but insufficient as the ledger: it follows only trade IDs in the given acknowledgement; if some fills fail and others confirm, it returns successful hashes rather than proving a full fill. Empty trade IDs can also produce an immediate return. Reconcile quantities per fill regardless. [Settlement helper implementation](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/_internal/actions/orders/settlement.py), [order lifecycle](https://docs.polymarket.com/concepts/order-lifecycle).

## Fees, budget, and exact P&L

Current sampled crypto fee schedule is `fee = shares × 0.07 × p × (1-p)`; only takers pay. At 0.70, five shares cost 3.50 plus about 0.07350 fee. That fee is **2.1% of purchase notional**, not 7% of all purchases; the fee rate varies with price. Round-trip execution incurs spread, possible slippage and potentially fees twice. Estimate all before entering, use live market parameters, and record estimates separately from charged amounts. [Fee rules](https://docs.polymarket.com/trading/fees).

SDK `max_spend` is explicitly an estimated all-in target using recently fetched fees, not a protocol-enforced final-fee cap. Fees can change at match time; a strict budget needs an additional verified fee allowance/reserve and account cash limit. Do not promise a precise $5 cap merely from `amount=5` or `max_spend=5`. The SDK's protected-price path signs at the supplied limit; it does not guarantee depth exists there. [Market-order source](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/_internal/actions/orders/market.py).

Exact fees are not present as `feeAmount` in current account REST/WS models. Fetch confirmed transaction receipts using the free RPC and decode the official **V2** `OrderFilled` event. Its indexed fields are orderHash, maker and taker; data are side, tokenId, makerAmountFilled, takerAmountFilled, **fee**, builder and metadata. Filter the verified exchange address and the bot's order hashes; deduplicate `(chain, txHash, logIndex)`. Do not count an order event and a matching summary as two fills.

Contract behavior: BUY charges collateral fee **on top of** maker cash; SELL deducts fee from cash proceeds. Thus confirmed BUY cost is makerAmountFilled + fee; confirmed SELL net proceeds are takerAmountFilled − fee, scaled with verified token decimals. Mark P&L provisional until receipt fees and inventory reconcile. The onchain field is named `fee`; internal Solidity variables sometimes use `feeAmount`. [Event ABI](https://github.com/Polymarket/ctf-exchange-v2/blob/main/src/exchange/interfaces/ITrading.sol), [actual transfers](https://github.com/Polymarket/ctf-exchange-v2/blob/main/src/exchange/mixins/Trading.sol), [fee denomination](https://github.com/Polymarket/ctf-exchange-v2/blob/main/src/exchange/mixins/Fees.sol), [official free RPC default](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/environments.py).

## Minimal architecture and operational constraints

Suggested responsibilities, not a demand for a large framework:

- `config`: one validated configuration source, resolved CLI overrides, hash recorded each run. Every advertised rule either executes or is removed/declared unsupported. Reject NaN, invalid time windows, unknown profiles, and budgets below exchange minimum. Do not implement the YAML's speculative hedge as part of this repair.
- `feeds`: current/next market metadata, both books, TWAP60s, source timestamps, connection state, and pre-start anchor recorder. Each decision receives one consistent snapshot.
- `strategy`: pure decision function over snapshot and account/risk state; returns enter/skip and machine-readable reasons plus actual measured BTC move. Scientific/sentiment choices are the root investigation's responsibility.
- `broker`: unified SDK adapter, price/size/fee checks, sign/persist/submit, actual receipt decoding and recovery. Real and paper brokers share decision inputs, but paper output must label fills as simulated.
- `ledger`: standard-library SQLite tables for runs, decisions, intents/orders, fill lifecycle/receipt events, balance snapshots and positions. Transactions reserve risk atomically. JSON-line event logs are a readable view, not the only recovery store.
- `runner`/CLI: foreground run, explicit paper/live mode, status, report, graceful stop. Existing shell files become thin repo-local launchers; PID and health state must match the actual process identity. Reports read ledger state even while the process runs or after it crashes.

A tiny live experiment can keep one position at a time, one entry per round, a fixed per-trade cap, fixed session cash-loss cap, finite session/trade limit, and no hedge or re-entry. Risk calculations include unsettled and unknown submissions. Stop entry on missing reference/anchor, stale or incoherent books, excessive chosen-side spread, insufficient depth, missing fees, duplicate round intent, clock skew, or unresolved account reconciliation.

Stops should use executable **net sell proceeds for the held quantity**, not Gamma odds or only the best bid. A price-protected close cannot guarantee liquidation. Near expiry, absent bids, a halt, or a disconnect can leave inventory exposed to full binary settlement loss; the genuine maximum per-trade loss is allocated cash plus fees, not the stop percentage. Keep monitoring/reconciliation and eventual resolution/redemption accounting even after entry timeouts or exit failure. If automatic redemption is out of initial scope, report claimable inventory explicitly and provide the manual route; do not silently write it off.

On SIGTERM: stop new entries, persist shutdown, cancel owned resting orders, reconcile partial fills, attempt only the already authorized bounded close policy, and persist unresolved inventory if it cannot finish. SIGKILL cannot be made graceful; restart recovery must cope with any interruption point. Do not auto-restart into fresh trading until recovery succeeds.

Handle 429 with bounded backoff; HTTP425 means matching-engine restart. Restart is followed by two minutes of post-only mode; a momentum bot should pause rather than changing a taker exit into a passive bet. Parse structured rejection details—some batch error responses can have `success:true` with an empty order ID and a nonempty error. HTTP503 cancel-only/post-only responses need state-aware handling, while ambiguous generic 5xx still requires reconciliation. [Engine modes](https://docs.polymarket.com/trading/matching-engine), [accepted/rejected response normalization](https://github.com/Polymarket/py-sdk/blob/polymarket-client-v0.9.0/src/polymarket/models/clob/order_response.py).

## What must be demonstrated before declaring it live-capable

1. Anonymous discovery, book snapshots and TWAP streaming work on the deployment machine; opening-anchor capture agrees with official later priceToBeat, including boundary/gap cases.
2. Deterministic verification covers partial entry/exit, timeout-after-accept, delayed confirmation, mixed confirmed/failed fills, cancellation racing with fills, restart after every persistence boundary, fee rounding, dust and empty books. These are meaningful tests for high-impact behavior, not tests that merely mirror functions.
3. Authenticated read-only preflight identifies wallet type/funder, pUSD balance/allowance and existing orders/inventory correctly. No setup transaction occurs in the loop.
4. A bounded explicitly authorized small live run demonstrates acknowledgement/hash agreement, fill finality, exact fees, inventory and cash reconciliation, and clean status/report behavior. A read-only inspection cannot honestly prove this final step.

Remaining uncertainty: the exact opening/closing observation selection when Chainlink has no boundary update is not established by the published sources reviewed. Resolve it through explicit source support or read-only empirical comparison before treating a recorded approximation as the official move anchor. All other core execution interfaces are available without paid market-data keys; reliable uptime, complete accounting and small real-fill verification are the work, not access to an expensive data vendor.

## Adapter interface addendum for implementation

Use async networking throughout: `AsyncPublicClient` for unauthenticated feeds and `AsyncSecureClient` for trading. Avoid synchronous network calls inside the event loop. `get_balance_allowance(asset_type="COLLATERAL")` returns raw integer pUSD balance and allowances; `asset_type="CONDITIONAL", asset_id=token_id` is correct for the sampled CTF market. A thin read-only `httpx.AsyncClient` JSON-RPC adapter can provide `eth_call` for pUSD `balanceOf(address)`, `decimals()`, and CTF `balanceOf(address,uint256)`, plus `eth_getTransactionReceipt`. Derive selectors with `eth_utils.keccak`; encode/decode arguments using `eth_abi`, both already SDK dependencies. Use the actual funder, not automatically the private-key signer. Verify chain 137 and use current official environment contract addresses.

For sampled CTF market order IDs, build the original exchange EIP-712 signable message with domain name `Polymarket CTF Exchange`, version `2`, chainId 137, and the correct standard/negative-risk exchange verifyingContract. Message fields, in official order: salt, maker, signer, tokenId, makerAmount, takerAmount, side (BUY=0/SELL=1), signatureType, timestamp, metadata, builder. Using `eth_account.messages.encode_typed_data`, hash `b"\x19" + signable.version + signable.header + signable.body` with keccak. This is the underlying exchange hash even for a POLY_1271 nested signature; do not hash the nested wrapper. Do not include expiration, postOnly, orderType, API owner, or signature. Preserve the signed payload's exact fields and use contract `hashOrder` read-only as an independent check. Future position-ID protocol markets have different exchange/version selection and should fail closed until supported.
