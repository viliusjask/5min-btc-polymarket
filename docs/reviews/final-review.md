### Important

**I1 / P1: Invalidate the execution cache as soon as a current-round official anchor or rule conflict is observed.**

Primary location: `src/btc5m/cli.py:212-218`. `LatestInput.observe` forwards authoritative observations to SQLite, but advances the execution invalidation generation only for `stream_unavailable` or `price_conflict` events carrying a spot/TWAP stream. An `anchor` event with `status="conflict"` is merely logged/emitted. The producer can emit exactly that event before awaiting more work: `MarketData._metadata` retains the original official anchor, sets its conflict flag and calls `_emit_anchor` (`src/btc5m/market_data.py:447-458`), then `snapshot` awaits the current CLOB/book reads (`src/btc5m/market_data.py:579-585`). During this interval the last published, still-fresh snapshot has the old nonconflicted Market. Both Engine consumption and its after-preparation recheck therefore see unchanged authorization (`src/btc5m/engine.py:84-89`, `:273-277`) and can submit a BUY at `:302-303` despite already having observed contradictory official evidence.

Reproduced with the actual `LatestInput`, `MarketData._metadata`, core, Engine, Broker, pinned SDK signing and SQLite. The existing synthetic account/HTTP fixtures supply all external data. After arming and confirming a valid candidate, the real Broker preparation completes; the real metadata producer then receives an official reference differing by USD1 and emits `anchor.status=conflict`, with no subsequent snapshot publication yet. The final Engine recheck leaves generation **0 -> 0**, returns **SUBMITTED**, and performs **one synthetic POST**. The durable order correctly becomes UNKNOWN when the synthetic response is lost, but the new entry should never have been posted.

The same consumer omission applies to a matched current-round delayed rule conflict: `_poll_due` sets `state.conflict` at `src/btc5m/market_data.py:520` and emits `metadata_unavailable` with `UNSUPPORTED_RULE` at `:533-539`; subsequent awaited polling/discovery can leave the old cache available. This counterpart follows directly from the inspected path; the executed reproduction specifically covers the anchor event.

This violates the immediate observed-invalidity cancellation contract in `docs/design.md:132-145` and the unknown/conflicting rule/anchor entry prohibition in `:39-53`. It is an integration defect, not a reason to relax the already-approved adapter conflict persistence.

Required correction: propagate definitive current-round anchor/rule invalidations immediately into the existing generation mechanism, before awaited polling resumes. Match their round identity so a late label/conflict for an unrelated historical round does not cancel a valid current candidate. Preserve the invalidation through later overwrites and abandon known-unposted preparation. Add producer-to-Engine regressions for conflict during account/preparation I/O, a later valid overwrite, and a historical-round control. Do not add a new trading policy or weaken the normal fresh-input checks.

Evidence: `work/final-review/check_integration_risks.py:23-61`, `work/final-review/integration-risk-results.json:2`.

**I2 / P2: Include task cancellation and transport teardown in the shutdown bound.**

Primary location: `src/btc5m/cli.py:606-609`; related `src/btc5m/cli.py:370-373`, `:617-626`, `src/btc5m/market_data.py:235-242`, and `src/btc5m/broker.py:139-142`.

The controller stops at its shutdown deadline (`src/btc5m/cli.py:522-525`), but that deadline does not enclose `_cancel`, `MarketData.__aexit__/close`, Broker close, or RPC close. The owner lock is released only by the final Ledger cleanup, after those awaited callbacks. A delayed transport close can therefore keep `run_live` pending, suppress its terminal report/exit and retain the wallet lock after `SHUTDOWN_DEADLINE`. Raising close exceptions is handled by AsyncExitStack, but a close that is still awaiting does not raise and is not bounded by that mechanism.

The named previously unproven concern is now reproduced. The real CLI and real MarketData run against anonymous external fixtures; only the SDK transport's close awaits a release event. With `--duration .01 --shutdown-seconds .01`, the ledger already records SHUTDOWN_DEADLINE and stop, yet **0.201 seconds of additional close waiting** leaves the run pending and a second Ledger owner receives WALLET_LOCKED. Releasing the fixture lets it return exit2 and releases ownership. The close is cooperative/cancellable; this does not require a coroutine that suppresses cancellation. No check intentionally leaves a task or journal owner running.

The documented operator contract calls the shutdown window bounded (`README.md:164-165`); help describes maximum additional reconciliation/protected-close seconds (`src/btc5m/cli.py:171`). The implementation establishes the controller's work budget, not the promised end-to-end shutdown behavior. Inspection of the installed pinned SDK's `AsyncPublicClient.close`, `AsyncSecureClient.close` and transport `close` confirms they await subordinate closes without providing an enclosing application deadline. This check does not claim to reproduce a particular live SDK hang or determine its frequency.

Required correction: establish and document a precise end-to-end policy for cancellation, teardown, final reporting and lock release. Carry the absolute remaining shutdown budget into these waits; prevent surviving execution tasks from operating after ownership is released. Include delayed-close and cancellation-path tests, including unresolved submitted state. If some pathological behavior cannot be bounded cooperatively, the operational guarantee and escalation/failure behavior must say so explicitly instead of promising a hard overall bound that the implementation does not enforce. Retaining durable unresolved exposure is required throughout.

Evidence: `work/final-review/check_integration_risks.py:80-127`, `work/final-review/integration-risk-results.json:22`.

**I3 / P2: Preserve a later explicit conflict in the per-round final-reference report.**

Primary location: `src/btc5m/cli.py:337-343`; producer `src/btc5m/market_data.py:460-476`.

The report reducer detects conflicts only when numeric `price` strings differ. The actual producer deliberately retains the original `state.final` after contradictory later metadata and emits that original price again with `status="conflict"`. The reducer neither checks this status nor updates an existing same-price row, so its `official_final_references_by_round` result retains the earlier `status="official"`. This can make an invalid eventual calibration label look authoritative even though the correct conflict remains present in the underlying observation history.

Reproduction uses the actual metadata producer, Ledger and report. Official `finalPrice=80000` followed by `finalPrice=80001` emits `[official, conflict]`, both with stored price `80000`; `cli.report` returns **official / 80000**. No account data, model return or fabricated fill is involved.

Required correction: treat any explicit producer conflict as a persistent per-round report conflict, including when the numeric value is unchanged, and ensure subsequent observations cannot heal it. Preserve safe provenance/evidence as appropriate. Add a producer-to-report regression plus controls for repeated compatible values, first-seen conflict and later observations. This should also correct retrospective reports from existing journals; no accounting migration is needed.

Evidence: `work/final-review/check_integration_risks.py:63-78`, `work/final-review/integration-risk-results.json:10`.
